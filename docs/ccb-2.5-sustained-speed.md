# CCB 2.5 持续能力测速设计

## 目的

CCB 2.4 的短请求只能回答“节点能否瞬时传得很快”，不能回答“节点能否持续供上当前视频”。2.5.0 将节点选择依据改为持续吞吐、低位速度、稳定率和连接可靠性，并保留 B 站原始源作为安全回退。

## 日常自动选线

每个视频开始播放时只启动一轮后台复核，不对每个分片重复测速：

| 阶段 | 候选数 | 测量 | 并发 | 用途 |
| --- | ---: | --- | --- | --- |
| 连通筛选 | 最多 7 | 1 字节 Range | 并行 | 排除 DNS、HTTP、权限和无资源节点 |
| 短筛 | 最多 4 | 256 KiB Range | 串行 | 快速淘汰明显慢节点，避免探针互相抢带宽 |
| 真实分段复测 | 最多 3 | 3 轮 × 3 MiB Range | 串行 | 分散测试视频中段，决定最终主节点和备用节点 |

持续复测会记录 onprogress 的增长曲线：

- 前 25%（最多 256 KiB）视为连接热身，不直接代表长期速度；
- 按至少 64 KiB 或 180 ms 的窗口计算瞬时吞吐；
- 持续低位为窗口速度的 P20；
- 尾段速度为热身之后剩余数据的平均速度；
- 持续速度 = min(持续低位, 尾段速度, 本次总速度)；
- 稳定率 = 持续低位 / 窗口中位数。

如果当前视频表示的带宽为 B Mbps，自动选线要求：

持续速度 >= max(1 Mbps, B + 0.35) × 2.5

同时要求三轮都完整下载、至少两轮在 4.5 秒内完成、稳定率至少 45%。当前节点若仍合格，新节点必须比它快 25% 才触发切换，避免线路来回抖动。当前视频切换清晰度后，如果缓存结果没有覆盖新的码率门槛，会重新复核。

播放器会保留已写入 `backup_url` 的备用顺序。实际播放出现媒体请求超时、网络错误、HTTP 错误，或在播放状态下缓冲降到 1.5 秒以内并触发 `waiting/stalled` 时，会将当前节点加入本视频的失败名单，并按已验证顺序切换到下一个备用；切换后页面与 Worker 不会再把请求改回已失败的主节点。

## 全节点排名

设置面板中的全节点测速分三步：

1. 全部节点进行两轮连通率测试；
2. 可连接节点进行 64 KiB 短筛；
3. 短筛前 20 名及核心节点进行两轮、每轮 1 MiB 的串行持续复测；文件大小已知时，两轮取视频中段的不同位置。

只有两轮持续复测均成功的节点才标记为“持续验证 2/2”。排名主要按持续低位速度、持续中位速度、稳定率、连接率、短筛成功率和 TTFB 综合计算。短筛结果不会伪装成持续验证结果。

测速流量的最坏估算约为：

- 日常单个视频：最多约 28 MiB（短筛约 1 MiB，加 3 个节点 × 3 轮 × 3 MiB）；
- 全节点：全部节点短筛流量 + 最多 24 个节点的两轮持续复测，当前目录规模约 79 MiB。

## 数据和兼容性

- 节点目录直接读取原项目 GitHub Raw，Pages 作为回退；每次新页面先检查 `info.json`，仅在 `lastSuccessTime` 变化时下载完整目录；
- 页面重新获得焦点超过 30 分钟后会再次检查版本，设置面板支持强制刷新；
- 2.5.0 使用独立的持续健康度和全量排名存储键，不复用 2.4 的短测排名；
- 2.4.1 文件不被覆盖，关闭自动选线或没有合格节点时回到手动/原始源；
- 正在测速的视频切换后会取消旧探针，避免旧任务继续占用带宽；
- `__INITIAL_STATE__` 中的推荐/预加载视频只做 URL 兼容改写，不触发日常测速；
- 全节点测速需要先播放并暂停一个视频，以取得当前可用的签名媒体地址。

## 验证

回归测试覆盖：

- 初始爆发、随后衰减的节点；
- 稳定节点与爆发节点的排序；
- 两轮持续复测中只成功一轮的节点；
- 视频码率门槛；
- 清晰度切换后的缓存隔离；
- 旧版排名存储不会被读取。
- 媒体 URL 判断只检查实际 hostname，不会被查询参数中的域名文本误触发；
- classic/module Worker 的相对地址会先转成绝对地址，临时 Blob URL 在 Worker 创建后释放；
- 生成后的用户脚本与 `src` 模板保持一致。
